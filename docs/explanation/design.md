# Design: how repo-tender works 🛠️

The bits worth knowing the *why* of. Understanding-oriented by design —
the how lives in the [tutorials](../tutorials/README.md) and
[how-to guides](../how-to/README.md).

## The cardinal rule: never lose your work

Every design decision below is downstream of this one. repo-tender only
ever fast-forwards a *clean* repo that is strictly behind. A dirty tree,
local commits the remote lacks, a detached HEAD, a non-default branch —
all *reported* and left untouched. There is no destructive path, not even
an opt-in flag. (The invariant and its consequences:
[what "evergreen" means](evergreen.md).)

## A periodic launchd job, not a resident daemon 🤖

`daemon install` writes a launchd plist; nothing else lingers. No socket,
no IPC, no in-process scheduler. launchd wakes a short-lived `sync` every
`refresh_interval` (`StartInterval` + `RunAtLoad`, deliberately no
`KeepAlive`); it fans out, writes state, and exits.

The trade: a resident daemon could react instantly to config changes or
push webhooks. But a resident process is another thing to monitor, leak,
and upgrade — and freshness on a 6-hour window has no use for instantaneity.
launchd already knows how to schedule, supervise, and log; duplicating it
inside a Ruby process would be strictly worse.

## Local-first, network-last 📡

Each sync pass checks on-disk facts before touching the network:

1. Is the checkout path present?
2. Is it clean, on the default branch?
3. Is `.git/FETCH_HEAD` younger than the refresh interval?

Only when local facts say "behind" does it fetch. Re-runs are cheap and
idempotent — which is exactly what makes a periodic, often-overlapping
schedule safe to run forever.

## Config vs. state 🗂️

Two files, on purpose:

- `config.yaml` (`$XDG_CONFIG_HOME/repo-tender/`) is *your* durable intent
  — which repos and orgs to tend, the refresh interval, concurrency.
  Hand-editable, validated on every load.
- `state.yaml` (`$XDG_STATE_HOME/repo-tender/`) is machine-managed —
  statuses, fetch times, org expansions. Never hand-edited; regenerated by
  sync passes.

Splitting them keeps machine rewrites (which happen constantly, and lose
YAML comments) away from the file you actually wrote. The config is
validated by a dry-validation contract at every boundary, so a typo in a
hand-edit fails loudly at load instead of weirdly at sync time.

## Concurrency on fibers ⚡

Sync fans out concurrently over [socketry/async] — a fiber scheduler, one
process, no thread soup — bounded by the `concurrency` setting (default 8)
so a large org sweep won't melt your machine. The same async discipline
carries the `cp -Rc` copy in `clone` and the `launchctl` calls in `daemon`.

[socketry/async]: https://github.com/socketry/async

## Fuzzy navigation is a shell contract

`repo-tender <fuzzy>` (any bare first token that isn't a registered
command) applies a deterministic 0/1/many contract: exactly one match →
the absolute path on the last stdout line, exit 0; zero matches → message
on stderr, exit 1. That contract is what the fish wrapper builds on: run
the command, and if the last output line is a directory, `cd` into it.
The CLI stays dumb; the shell stays scriptable.

The matcher is a case-insensitive subsequence match against `owner/name`
(host excluded from matching, included in the resolved path), ranked by
contiguity, word boundaries, and earliness, with a deterministic total
order for ties (`lib/repo_tender/nav.rb`).
